# Защита ПР5: все 25 пунктов

Примеры Roomly из таблицы методички заменены нашей предметной областью:
помещение -> инцидент, `room_detail` -> `incident_detail`,
`find_room_by_id` -> `find_incident_by_id`, `/rooms/` -> `/incidents/`.
Это разрешено примечанием к таблице: демонстрируется индивидуальный проект.
Названия полей своей модели называй точно: `id`, `title`, `priority`.

## До начала опроса

В VS Code открой корень TRPNBF. Подготовь вкладки:
`incident_site/settings.py`, `incident_site/urls.py`, `manage.py`,
`homepage/views.py`, `web_incidents/urls.py`, `web_incidents/views.py`,
`storage.py`, `incidents.py`, `models/incident.py`, `data/incidents.json`.
Открой два терминала в корне: первый для сервера, второй для проверок.

После установки зависимостей и миграций по README:

```powershell
.\.venv\Scripts\python.exe manage.py check
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m flake8 .
$env:DJANGO_DEBUG = "False"
.\.venv\Scripts\python.exe manage.py runserver
```

Переменная `DJANGO_DEBUG` должна задаваться в том окне, где запускается сервер.
Для защиты она выключает отладку и позволяет показать пользовательскую 404.
Открой в браузере `/`, `/incidents/`, `/incidents/1/`, `/statistics/`,
`/nonexistent/`, `/incidents/999/` на http://127.0.0.1:8000.
У исходного JSON есть инциденты 1 и 2; ID 999 отсутствует.

Пять минут на 25 вопросов - примерно 12 секунд на пункт. Сначала выучи краткие
ответы ниже, затем отрепетируй переход к нужному фрагменту. Опрос по методичке
останавливается на первом неправильном ответе. Дополнительные пояснения нужны
для понимания и уточняющих вопросов; их не обязательно произносить целиком.

## 1. Структура Django-проекта

**Покажи:** пакет `incident_site/`, затем `settings.py` и `urls.py`.

**Краткий ответ:** «settings.py содержит настройки: приложения, отладку,
разрешенные адреса, язык и путь к данным. Корневой urls.py направляет запросы
в URLconf приложений. incident_site - конфигурационный пакет всего сайта».

Проект объединяет приложения. Приложение отвечает за конкретную часть:
главную, инциденты или статистику. `asgi.py` и `wsgi.py` - точки входа для
серверов соответствующих типов; `__init__.py` делает каталог пакетом Python.

## 2. Проверка и запуск

**Покажи:** `manage.py`, особенно `DJANGO_SETTINGS_MODULE` и
`execute_from_command_line(sys.argv)`.

**Краткий ответ:** «manage.py - точка входа команд Django с настройками проекта.
Проверка: python manage.py check. Запуск: python manage.py runserver».

У нас Python из окружения вызывается как `.\.venv\Scripts\python.exe`.
`check` проверяет конфигурацию, но не заменяет тесты страниц и бизнес-логики.
`runserver` запускает сервер разработки; Ctrl+C его останавливает.

## 3. Регистрация приложений

**Покажи:** `INSTALLED_APPS` в `incident_site/settings.py`.

**Краткий ответ:** «Зарегистрированы HomepageConfig, WebIncidentsConfig и
DashboardConfig. Django использует этот список для подключения приложений,
их конфигурации, моделей, миграций и поиска ресурсов».

Важная точность: незарегистрированное приложение не обязательно сразу сломает
эти простые views. Python может импортировать функции, а `include()` может
подключить URLconf и без регистрации. Но приложение не будет полноценно
участвовать в механизмах Django: его модели, миграции, шаблоны и статика
могут не обнаруживаться корректно. Регистрация не создает маршруты сама:
маршруты подключаются отдельно в `urls.py`.

## 4. Распределение страниц

**Покажи:** каталоги `homepage`, `web_incidents`, `dashboard` и их URLconf.

**Краткий ответ:** «homepage отвечает за главную и общую 404, web_incidents -
за список и карточку, dashboard - за статистику. Отдельных страниц
пользователей пока нет, имена автора и исполнителя показаны в карточке».

`django.contrib.auth` уже предоставляет встроенную модель учетной записи.
Но наш `models.users.User` - обычный класс ПР3, а не та модель Django.
Он пока не связан с входом на сайт. Создание собственного приложения людей
технически возможно; в этой работе оно просто не нужно.
`web_incidents` не называется `incidents`, чтобы не перекрыть файл
`incidents.py`, из которого импортируется логика ПР3.

## 5. DEBUG и ALLOWED_HOSTS

**Покажи:** `DEBUG`, `ALLOWED_HOSTS` в settings.

**Краткий ответ:** «DEBUG включает технические страницы ошибок. Для нашей
404 нужна отключенная отладка. ALLOWED_HOSTS перечисляет допустимые имена
хостов; у нас разрешены локальные адреса».

Здесь `DEBUG` читается из переменной среды `DJANGO_DEBUG`. Если она не задана,
значение по умолчанию True. Перед отключением проверяем разрешенные хосты и
наличие обработчика 404. Неподходящий Host дает 400; это не ошибка поиска
инцидента. При отключенной отладке встроенный сервер обычно не раздает
статические файлы; Bootstrap загружается отдельно через CDN.
Для реального размещения нужны настоящий домен и отдельный секретный ключ.

## 6. Проход через два URLconf

**Покажи:** эти строки в двух файлах:

```python
# incident_site/urls.py
path("incidents/", include("web_incidents.urls")),

# web_incidents/urls.py
path("<int:incident_id>/", views.incident_detail, name="incident_detail"),
```

**Краткий ответ:** «Для /incidents/999/ корневой URLconf обрабатывает
incidents/. include передает оставшуюся часть 999/ приложению.
Его URLconf преобразует 999 в int и вызывает incident_detail».

В `path()` шаблоны записываются без начального `/`. `include()` позволяет
хранить маршруты каждого приложения отдельно.

## 7. Связь URL и view

**Покажи:** маршрут из предыдущего пункта и
`def incident_detail(request, incident_id)`.

**Краткий ответ:** «views.incident_detail - функция обработки.
incident_id передается именованным аргументом. При переименовании функции
меняем определение и ссылку на нее в URLconf. name - имя маршрута,
используемое reverse для создания адреса».

`name="incident_detail"` не вызывает функцию по ее имени автоматически.
Функция задается вторым аргументом `path()`; name служит именованию URL.
`app_name="web_incidents"` добавляет пространство имен:
`reverse("web_incidents:incident_detail", args=[1])` дает `/incidents/1/`.
Ссылки во views и page используют `reverse()`, а не дублируют пути вручную.

## 8. Конвертер int

**Покажи:** `/incidents/abc/` и `/incidents/999/` в браузере.

**Краткий ответ:** «int принимает числовую часть URL и передает Python int.
abc не подходит маршруту, view не вызывается. 999 подходит маршруту,
но наличие объекта проверяется уже внутри view».

Конвертер не обращается к JSON и не проверяет, существует ли такой ID.
Отрицательный ID также не соответствует встроенному конвертеру int.

## 9. Путь HTTP-запроса к главной

**Покажи:** `path("", include("homepage.urls"))`, затем
`homepage/urls.py` и `index()` в `homepage/views.py`.

**Краткий ответ:** «Браузер отправляет GET /. Django проходит корневой
URLconf и URLconf homepage, вызывает index(request), получает HttpResponse
с HTML и отправляет его браузеру».

Браузер разбирает HTML и отдельно загружает Bootstrap CSS по ссылке.
Сервер возвращает текст разметки, а ее отображением занимается браузер.

## 10. request и HttpResponse

**Покажи:** `def index(request)` и строку `return HttpResponse(...)`.

**Краткий ответ:** «Django создает HttpRequest из входящего запроса и
передает его первым аргументом. View возвращает HttpResponse, содержащий
тело ответа, заголовки и статус. Обычная строка не является HTTP-ответом».

В request доступны `request.method`, `request.path`, `request.GET`,
`request.POST`. На этом этапе главная не использует содержимое request,
но параметр нужен для вызова Django. Если вернуть просто строку, дальнейшая
обработка ответа сломается, обычно возникнет AttributeError и ответ 500.

## 11. Как получается HTML

**Покажи:** переменную `content` в index, вызов `page()` и
`<main class="container">{content}</main>` в page.

**Краткий ответ:** «index собирает content, передает его в page вместе
с title. page вставляет content внутрь main общего HTML. Затем
HttpResponse передает результат браузеру».

Другой текст в content изменит основную часть страницы, общий каркас
останется. page возвращает Python-строку, а HttpResponse превращает ее
в тело HTTP-ответа. Это два разных действия.

## 12. Назначение page()

**Покажи:** всю функцию `page(title, content)`.

**Краткий ответ:** «page убирает дублирование общего HTML: doctype,
head, подключение CSS, навигацию, main и footer. Конкретная view передает
заголовок вкладки и содержимое своей страницы».

Заголовок title вставляется в `<title>` и экранируется. content - уже
подготовленная разметка, поэтому его целиком экранировать нельзя:
вместо заголовков и кнопок браузер показал бы текст HTML-тегов.
Текстовые значения данных экранируются перед включением в content.

## 13. Повторное использование каркаса

**Покажи:** вызовы page в `index()` и `dashboard.views.statistics()`.
Затем открой `/` и `/statistics/`.

**Краткий ответ:** «Каркас и навигация одинаковые. Главная передает
описание и кнопки, статистика - количество и распределение инцидентов.
Одна функция page подходит обеим страницам».

Изменение навигации в page появится на всех страницах без копирования кода.
На следующих практических этот каркас можно перенести в базовый шаблон.

## 14. Изменение заголовка

**Покажи и сделай:** в `homepage/views.py`, в конце index, временно замени:

```python
return HttpResponse(page("Учет инцидентов - главная", content))
```

на:

```python
return HttpResponse(page("Главная служба поддержки", content))
```

Сохрани и обнови `/` в браузере. Посмотри на название вкладки.

**Краткий ответ:** «Первый аргумент page меняет title вкладки.
Чтобы изменить видимый заголовок, меняю h1 в content конкретной view.
Саму общую функцию page менять не нужно».

Автоперезапуск работает при обычном runserver. Если сервер запущен с
`--noreload`, останови его и запусти заново. После демонстрации верни строку.

## 15. Bootstrap

**Покажи:** `BOOTSTRAP_CSS`, `<link ... rel="stylesheet">` в page и
`btn btn-primary`, `card`, `badge`, `list-group` в разметке.

**Краткий ответ:** «Bootstrap - CSS-фреймворк. link подключает его стили,
а классы оформляют кнопки, карточки, списки и адаптивную сетку.
Без подключения Bootstrap эти стили исчезнут, данные и ссылки останутся».

Наш собственный `<style>` останется даже без Bootstrap: он задает фон,
цвета навигации, шрифт и перенос описания. Поэтому страница не станет
совсем без оформления. Полная загрузка CDN требует интернета.

## 16. Загрузка и поиск

**Покажи:** `storage.load_incidents()` и
`incidents.find_incident_by_id()`.

**Краткий ответ:** «load_incidents возвращает список объектов Incident.
find_incident_by_id принимает список и ID, возвращает объект или None.
В incident_detail сначала загружаются данные, затем ищется объект».

Поиск использует сохраненную функцию `get_incident()` ПР3. Та возвращает
объект или вызывает KeyError. Новый адаптер перехватывает только KeyError
и возвращает None; это позволяет явно показать ветвление во view и
не менять контракт старой консольной функции.

## 17. Путь данных из JSON

**Покажи последовательно:** `settings.INCIDENTS_FILE`, data/incidents.json,
`load_incidents`, `decode_incidents`, `Incident(...)`, `incident_detail`.

**Краткий ответ:** «Путь задается в settings относительно корня проекта.
json.load читает записи; decode_incidents проверяет поля и создает
User, Executor, Incident. Список объектов приходит в view, поиск
выбирает нужный инцидент».

`json.load()` дает списки и словари Python. `decode_incidents()` превращает
их в объекты предметной области. Словари не являются теми объектами,
которые затем отображаются в карточке. Совпадающие люди одной роли
получают общую ссылку по имени, как в ПР3.

## 18. Использование объекта во view

**Покажи:** `incident = find_incident_by_id(...)` и разметку успешной карточки.

**Краткий ответ:** «Поиск возвращает Incident. View читает его id, title,
description, priority, status, created_at. Через incident.user.name
читает имя связанного автора, через incident.executor.name - исполнителя».

Если исполнитель отсутствует, он равен None и выводится «Не назначен».
`Incident` здесь обычный Python-класс из `models/incident.py`.
Файлы `models.py` Django-приложений пока не содержат предметных ORM-моделей.

## 19. Изменение атрибута и HTML

**Покажи и сделай:** в `data/incidents.json` у записи с ID 1 временно
замени title на «Проверка на защите». Сохрани, обнови `/incidents/1/`.
Новое название появится в карточке и в заголовке вкладки.
Обнови `/incidents/` - ссылка также получит новое название.

**Краткий ответ:** «При каждом запросе JSON читается заново. Меняется
атрибут загруженного объекта, и f-строка включает новое значение в HTML».

Изменять можно и priority, но только на 1, 2 или 3. Изменения должны
проходить проверки объекта. После демонстрации верни прежнее название.
Не меняй ID на повторяющийся и не повреждай синтаксис JSON.

## 20. Реальные типы данных

**Покажи:** JSON, конструктор Incident и обращения к полям во view.

| Значение | Тип после загрузки | Как отображается |
| --- | --- | --- |
| `incident.id` | `int` | Число ID |
| `incident.title`, `description` | `str` | Экранированный текст |
| `incident.priority` | `int`, 1-3 | Число и `priority_name` |
| `incident.priority_name`, `status` | `str` | Текст, статус внутри badge |
| `incident.created_at` | `str` формата ISO 8601 | Текст даты |
| `incident.user` | `User` | Имя через `.name` |
| `incident.executor` | `Executor` или `None` | Имя или «Не назначен» |

**Краткий ответ:** «ID и приоритет - int, название и статус - str.
Автор - объект User, исполнитель - Executor или None.
Дата в этой модели хранится строкой ISO 8601».

В JSON люди записаны строками имен, но загрузчик превращает их в объекты.
Дата проверяется `datetime.fromisoformat()`, однако в атрибут сохраняется
исходная строка, а не datetime. JSON null преобразуется в Python None.

## 21. Общая ошибка 404

**Покажи:** `ROOT_URLCONF`, `handler404` в корневом urls.py,
`page_not_found(request, exception)` и `/nonexistent/`.

**Краткий ответ:** «Django берет handler404 из корневого URLconf.
При неизвестном URL и DEBUG=False вызывает page_not_found,
которая создает страницу через page и возвращает HttpResponse со статусом 404».

Обработчик получает request и exception. Exception - причина ошибки;
мы не показываем ее пользователю. Если объявить handler404 только
в URLconf приложения, Django не будет использовать его как общий обработчик.

## 22. Нет маршрута или нет ресурса

**Покажи:** `/incidents/abc/` и `/incidents/999/`.

**Краткий ответ:** «abc не соответствует маршруту: view не запускается,
срабатывает общий handler404 при выключенной отладке.
Для 999 маршрут есть: view загружает JSON, не находит объект и сама
возвращает ответ 404».

Общий handler404 также используется при исключении `Http404` из view
при DEBUG=False. Но наш явный `return HttpResponse(..., status=404)`
не возбуждает исключение и не вызывает handler404 автоматически.
Две страницы имеют один HTTP-статус, но разные причины и сообщения.

## 23. Ветвление во view

**Покажи:** `if incident is None:` в incident_detail.

**Краткий ответ:** «Если поиск вернул None, отправляется страница ошибки.
Если вернул объект, выполнение продолжается и формируется карточка.
Без проверки обращение к атрибутам None вызовет AttributeError».

Ранний `return` завершает функцию, поэтому код успешной карточки
не выполнится для отсутствующего инцидента. Отдельный else не нужен.

## 24. Зачем проверять отсутствие объекта

**Покажи:** контракт `Incident | None` и ветку проверки.

**Краткий ответ:** «None обозначает, что объекта нет. У None нет атрибутов
инцидента, например executor или title. Проверка дает понятный ответ 404
вместо внутренней ошибки сервера 500».

В нашем коде без проверки первым сломается обращение к incident.executor.
На практике пользователь может вручную ввести любой числовой ID,
поэтому нельзя полагаться только на корректные ссылки списка.

## 25. Временная замена 404 на 403

**Покажи и сделай:** только в ветке `if incident is None` файла
`web_incidents/views.py` замени:

```python
return HttpResponse(page("Инцидент не найден", content), status=404)
```

на:

```python
return HttpResponse(page("Инцидент не найден", content), status=403)
```

Не меняй status=200 успешной карточки и status=404 общего handler404.
Сохрани файл, обнови `/incidents/999/`. В DevTools браузера (F12) открой
Network, обнови страницу, выбери запрос 999/ и покажи Status Code: 403.
Или во втором PowerShell выполни:

```powershell
curl.exe -i http://127.0.0.1:8000/incidents/999/
```

В начале ответа будет `HTTP/1.1 403 Forbidden`.

**Краткий ответ:** «Меняется параметр status ответа в ветке отсутствующего
объекта. 404 означает, что ресурс не найден; 403 - что доступ запрещен.
403 здесь только демонстрация, для отсутствующего объекта корректен 404».

После демонстрации верни status=404. Не добавляй лишний маршрут или
параметр для смены статуса: преподаватель проверяет умение изменить код.
Если оставить 403, тест отсутствующего инцидента правильно перестанет проходить.

## После репетиции

Верни заголовок, JSON и status=404. Останови сервер Ctrl+C.
Проверь, что учебные изменения не остались:

```powershell
git diff
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m flake8 .
.\.venv\Scripts\python.exe manage.py check
```

Не выполняй reset --hard ради отмены репетиции: это может удалить другие
незакоммиченные изменения. Верни три значения вручную.

## Короткая связная речь о проекте

«Моя предметная область - учет инцидентов. В ПР3 были обычные классы
Incident, User и Executor, консольное меню, JSON и тесты. В ПР5 я добавил
Django-проект incident_site и три приложения: homepage, web_incidents,
dashboard. Браузер отправляет HTTP-запрос; URLconf выбирает view.
View использует те же функции и объекты ПР3, формирует HTML через page
и возвращает HttpResponse. Есть список, карточка и статистика, а также
две обработки 404. Инциденты пока хранятся в JSON. Формы, шаблоны и
предметные ORM-модели будут следующими этапами».
